## 1. 新功能：刪除

### 要解決的問題

刪掉一個物件很簡單，難的是**連在它身上的線**。如果只把物件從清單移除，連線的 Port 還指向那個已經不在畫布上的物件，會留下一條「一端懸空」的線。

### 做法：三步驟

```java
// Canvas.deleteSelected()
// 1. 收集「所有會消失的圖形」，包含群組裡面的子孫
Set<Shape> removedShapes = new HashSet<>();
for (Shape s : selectedShapes) collectWithDescendants(s, removedShapes);

// 2. 移除選取的圖形
shapes.removeAll(selectedShapes);

// 3. 移除依附在被刪除圖形上的連線
shapes.removeIf(s -> s.isAttachedToAny(removedShapes));
```

### 為什麼要遞迴收集群組子孫？

```
A、B 被群組成 G；C 有一條線連到 A。

刪除 G 時：
  線的終點 Port 屬於 A（不是 G）
  → 集合裡只放 G 的話，線問「A 在不在集合裡？」→ 不在 → 線被留下來（bug）
  → 遞迴把 A、B 也放進集合 → 線被正確刪除
```

`collectWithDescendants` 走訪 `getComponents()`：一般圖形回傳空清單，遞迴自然停止。這就是 **Composite Pattern 透明介面**的好處——不用判斷「是不是群組」。

### 為什麼用 `isAttachedToAny()` 而不是 `instanceof ConnectionLine`？

延續專案慣例：**依型別決定行為時，用多型取代 instanceof**。

```java
// Shape（預設）：我不依附任何人
public boolean isAttachedToAny(Set<Shape> removed) { return false; }

// ConnectionLine（覆寫）：我的兩端只要有一端的主人被刪，我就依附在它身上
public boolean isAttachedToAny(Set<Shape> removed) {
    return removed.contains(startPort.getParent()) || removed.contains(endPort.getParent());
}
```

### 快捷鍵怎麼綁的？

```java
deleteItem.setAccelerator(KeyStroke.getKeyStroke(KeyEvent.VK_DELETE, 0));
```

把快捷鍵掛在**選單項目**上，而不是在 Canvas 上寫 `KeyListener`。好處：只要主視窗有焦點就有效，不必煩惱 Canvas 有沒有拿到鍵盤焦點（JPanel 被滑鼠點擊時不會自動取得焦點，KeyListener 常因此收不到按鍵）；選單上還會自動顯示快捷鍵提示。

## 2. 新功能：連線可被選取

原本 `ConnectionLine.contains()` 固定回傳 `false`，所以線點不到、也就無法刪除。

```java
@Override
public boolean contains(Point p) {
    double distance = Line2D.ptSegDist(x1, y1, x2, y2, p.x, p.y);
    return distance <= HIT_TOLERANCE;   // 5 像素
}
```

- **`Line2D.ptSegDist`**：點到「線段」的最短距離。注意是**線段（Segment）**，不是無限長的直線——點在延長線上但超出兩端時，距離以端點計算，不會誤判。
- **為什麼要容許誤差**：線只有 1 像素寬，要求滑鼠剛好點在線上，使用者幾乎點不到。
- **與物件重疊時誰優先**：連線在清單最前面（最底層），`getTopShapeAt()` 從上層往下找，所以會先命中物件；只有點在線「露出來的地方」才會選到線。
- **視覺回饋**：選取時藍色粗線（`BasicStroke(2.5f)`）、懸停時藍色細線；畫完一定要把筆觸還原，以免影響後面的圖形。

## 3. 新功能：存檔 / 讀檔（Java 序列化）

### 為什麼選 Java 序列化？

| 方案 | 優點 | 缺點 |
|---|---|---|
| **Java `Serializable`（採用）** | 程式碼最少；自動保留物件之間的共用參照 | 二進位檔不可讀；改類別欄位後舊檔可能讀不回來；有反序列化安全風險（已用白名單防範） |
| 自訂 JSON | 可讀、可版控、沒有反序列化風險 | 要手寫序列化與解析，連線需用「物件 id + Port 編號」重建參照 |

### 關鍵一：讓類別可以被序列化

```java
public abstract class Shape implements Serializable {
    private static final long serialVersionUID = 1L;
```

- `Serializable` 是**標記介面（Marker Interface）**：沒有任何方法，只是告訴 JVM「允許序列化」。子類別自動繼承這個身分。
- `Port` 也要實作：序列化會沿著參照一路寫下去，只要遇到一個不可序列化的物件，就會丟出 `NotSerializableException`。
- **`serialVersionUID`**：版本號。不手動宣告的話，JVM 會依類別內容自動計算，類別稍微改動就變，舊檔就讀不回來。固定成 `1L` 代表「沒刻意改版號就視為相容」。

### 關鍵二：整個清單「一次」寫出

```java
out.writeObject(new ArrayList<>(shapes));
```

```
物件關係：
  ConnectionLine ──參照──> Port ──屬於──> BasicObject
                              ↑
  BasicObject ──持有──────────┘   ← 同一個 Port 物件
```

Java 序列化在**同一次** `writeObject` 中會記住「寫過哪些物件」，同一個物件第二次只寫參照編號。所以讀回來後，連線參照的 Port 和物件持有的 Port **仍是同一個物件**——拖曳物件時，連線照樣會跟著走。

如果分成多次 `writeObject` 分別寫，讀回來就會變成兩個內容相同但互不相干的 Port，連線就斷了。

### 關鍵三：反序列化白名單（安全性）

`readObject()` 會**依照檔案內容**建立物件。惡意製作的檔案可以塞入 classpath 上某些危險類別的組合（Gadget Chain），在「讀檔的過程中」就觸發執行任意程式碼——這是 Java 史上很有名的漏洞類型。

防護方式：JDK 9 加入的 `ObjectInputFilter`，只放行我們需要的類別：

```java
ObjectInputFilter.Config.createFilter(
    "maxdepth=200;maxrefs=1000000;maxbytes=52428800;"
    + "shape.*;java.util.*;java.lang.*;java.awt.Color;!*"
);
```

| 規則 | 意思 |
|---|---|
| `shape.*` | 允許本專案的圖形類別 |
| `java.util.*`、`java.lang.*` | 允許 ArrayList、String、Enum 等 |
| `java.awt.Color` | 允許顏色 |
| `!*` | 其他一律拒絕（由左到右比對，第一個符合的規則決定結果） |
| `maxdepth / maxrefs / maxbytes` | 限制巢狀深度、物件數量、檔案大小，防止耗盡記憶體 |

> ⚠️ 之後若在 `Shape` 加上新的欄位，型別必須在白名單內，否則讀檔會被拒絕。

### 關鍵四：讀檔後重設狀態

存檔當下的「選取中」「懸停中」也被寫進檔案了，所以 `Canvas.replaceAllShapes()` 讀回後會：清掉 `floatingShape`、把所有圖形（含群組子孫）設為未選取、未懸停，畫面才會是乾淨的。

### 這裡用了 instanceof，不是違反慣例嗎？

```java
if (!(data instanceof List)) throw new InvalidObjectException(...);
```

不衝突。專案慣例針對的是「**依型別決定行為**」（應該用多型）；這裡是「**驗證不可信任的外部輸入**」——檔案內容可能是任何東西，轉型前必須先確認型別。

## 4. 新功能：匯出 PNG

```java
// Canvas.renderToImage()
BufferedImage image = new BufferedImage(w, h, BufferedImage.TYPE_INT_RGB);
Graphics2D g2 = image.createGraphics();
try {
    g2.setColor(Color.WHITE); g2.fillRect(0, 0, w, h);   // 新影像預設全黑，要先塗白
    // 暫時清除選取 / 懸停 → 畫 → 還原
    drawAllShapes(g2);
} finally {
    g2.dispose();
}
```

| 設計點 | 說明 |
|---|---|
| **`draw` 不用改** | `createGraphics()` 給的也是 `Graphics` API，畫在螢幕還是記憶體中的影像，對 `draw` 沒有差別——這就是抽象化的威力。 |
| **不含控制點** | 先記住誰是選取 / 懸停中，全部清除後再畫，畫完還原。使用者的操作狀態不受影響。 |
| **不含預覽框** | 匯出時不呼叫 `currentMode.draw()`。 |
| **完整匯出** | 影像大小取「畫布大小」與「所有圖形最右 / 最下邊界 + 20px」的較大值，拖到畫布外的圖形也會被匯出。 |
| **`dispose()`** | 自己 `createGraphics()` 的畫筆要自己釋放；`paintComponent` 的 `g` 是 Swing 借的，不能 dispose。 |
| **職責分離** | `Canvas` 負責畫出影像，`DiagramFileIO` 只負責寫檔，彼此不認識。 |

## 5. 行為改動

### 5.1 連線不會浮到上層

選取物件時，`floatToFront` 會把它暫時移到最上層。連線變得可以點選後，若也被浮起，就會蓋到物件上面，破壞「連線永遠在底層」的規則。所以：

```java
public void floatToFront(Shape s) {
    restoreFloating();
    if (s.isBackgroundLayer()) return;   // 連線不浮起
    ...
}
```

### 5.2 連線不會被收進群組

框選時，兩端都在框內的連線也會被選到。若連線被收進群組：

- `CompositeObject.updateBounds()` 會讀到連線沒有意義的 x / y / width / height，算出**錯誤的群組外框**。
- 連線本來就綁在 Port 上，物件被群組後一起移動時，線自然會跟著走，根本不需要群組管理。

所以 `groupSelected()` 跳過 `isBackgroundLayer()` 的圖形並取消其選取。（這個問題在框選時其實早就存在，只是連線變得可選取後更容易遇到。）

### 5.3 `ConnectionLine.move()` 改為空實作

連線的位置完全由兩端的 Port 決定。物件和連線一起被選取拖曳時，`SelectMode` 會對每個選取的圖形呼叫 `move()`；沿用基底版本只會改到沒意義的 x / y。改成空實作讓語意更明確。

### 5.4 JDK 需求 8 → 9

`ObjectInputFilter` 是 JDK 9 才加入的 API。

## 6. Bug 修復

### 6.1 Group / Ungroup 監聽器被註冊兩次

```java
groupItem.addActionListener(e -> canvas.groupSelected());
// ...幾行之後...
groupItem.addActionListener(e -> canvas.groupSelected());   // 重複了
```

`addActionListener` 是**累加**而不是覆蓋，所以點一次 Group 會執行兩次 `groupSelected()`。之前沒出事，是因為第二次執行時只剩一個群組被選取，「至少 2 個」的條件不成立——屬於潛在 bug，邏輯一改就可能爆。修法：刪除重複的那兩行。

### 6.2 標籤文字沒有真正置中

```java
// 修正前
g.drawString(label, x + width/2, y + height/2);
```

`drawString(text, x, y)` 的座標**不是文字的左上角**：

- `x` 是文字的**最左端** → 文字從中心點往右延伸，整體偏右。
- `y` 是文字的**基線（baseline）**，也就是英文字母底部所坐的那條線 → 整體偏上。

```java
// 修正後：用 FontMetrics 量出文字實際大小
FontMetrics fm = g.getFontMetrics();
int textX = x + (width - fm.stringWidth(label)) / 2;
int textY = y + (height - fm.getHeight()) / 2 + fm.getAscent();
```

| FontMetrics 方法 | 意思 |
|---|---|
| `stringWidth(s)` | 整段文字的像素寬度 |
| `getHeight()` | 一行文字的總高度（ascent + descent + leading） |
| `getAscent()` | 基線以上的高度 |

垂直置中的算法：先算「文字框頂端」該放的位置 `(height - fontHeight) / 2`，再加上 `ascent` 換算成 `drawString` 需要的基線位置。

### 6.3 連線箭頭被物件遮住

**現象**：拖曳物件後，Composition 的菱形箭頭有一半被方塊蓋住。

**原因**：連線（含箭頭）整條都在最底層畫；箭頭尖端落在物件邊緣的 Port 上，斜向靠近時有一半在物件內部，後畫的物件就把它蓋掉了。

**修法**：把連線拆成兩層——線身用 `draw()` 留在底層，箭頭用新的多型掛勾 `drawOverlay()` 在所有物件畫完後才畫。

```
繪製順序（由下到上）：
  ① 背景  ② 第一輪 draw()（線身 → 物件）  ③ 第二輪 drawOverlay()（箭頭）  ④ 模式的暫時 UI
```

- `Shape.drawOverlay()` 預設空實作，只有 `ConnectionLine` 覆寫；`CompositeObject` 轉交給子圖形（Composite Pattern）。
- 線身與箭頭都呼叫 `applyLineStyle()` 設定顏色與筆觸，確保選取時兩層一起變藍。
- `paintComponent` 與 `renderToImage` 共用 `drawAllShapes()`，螢幕與匯出結果一致。

詳細原理見〈繪圖機制筆記〉5.5 節。

## 7. 這次用到的 Java 機制速查

| 機制 | 用在哪 | 一句話 |
|---|---|---|
| `Serializable` / `serialVersionUID` | `Shape`、`Port` | 標記可序列化；固定版本號避免小改動就讀不回舊檔 |
| `ObjectOutputStream` / `ObjectInputStream` | `DiagramFileIO` | 物件 ↔ 位元組；同一次寫入會保留共用參照 |
| `ObjectInputFilter`（JDK 9+） | `DiagramFileIO.load` | 反序列化白名單，防範 Gadget Chain 攻擊 |
| try-with-resources | `DiagramFileIO` | 區塊結束自動 `close()` 串流，例外時也一樣 |
| 串流層層包裝（Decorator Pattern） | `DiagramFileIO` | `FileOutputStream` → `BufferedOutputStream` → `ObjectOutputStream` |
| multi-catch `catch (A \| B ex)` | `UMLEditor.openDiagram` | 一個 catch 接多種例外，處理方式相同時避免重複 |
| `Line2D.ptSegDist` | `ConnectionLine.contains` | 點到線段的最短距離 |
| `FontMetrics` | `BasicObject.draw` | 量出文字實際寬高，用於置中 |
| `BufferedImage` + `createGraphics()` | `Canvas.renderToImage` | 在記憶體中的影像上作畫，用完要 `dispose()` |
| `ImageIO.write` | `DiagramFileIO.exportPng` | 影像寫成檔案；回傳 false 代表沒有對應的編碼器 |
| `JFileChooser` + `FileNameExtensionFilter` | `UMLEditor.chooseFile` | 模態檔案對話框，只顯示指定副檔名 |
| `setAccelerator(KeyStroke)` | `UMLEditor` 選單 | 選單快捷鍵，主視窗有焦點就有效 |
| `Collection.removeIf(Predicate)` | `Canvas.deleteSelected` | 傳入 Lambda 條件，符合的元素被移除 |
| `HashSet` | `Canvas.deleteSelected` | `contains()` 為 O(1)，比 List 的 O(n) 快 |

## 8. 怎麼驗證的

1. **無頭測試**（不開視窗，直接呼叫程式）16 項：點選連線的距離判定、群組不含連線且外框正確、存讀檔往返後標籤顏色與 Port 參照都保留、刪除群組時連帶清除子物件的連線、白名單會拒絕 `java.io.File`、非清單資料被拒、匯出影像不含控制點且選取狀態有還原。
2. **實際 GUI 操作**：用 `java.awt.Robot` 送出真實的滑鼠與鍵盤事件，從 `Main.main` 啟動程式後依序建立物件與連線 → 點選連線 → Ctrl+S 存檔 → Ctrl+E 匯出 → Delete 刪線 → Delete 刪物件 → Ctrl+O 讀檔 → 拖曳物件，每一步截圖確認畫面，並對照畫布的內部狀態。

## 9. 口試速答

- **刪除物件時，連線怎麼處理？**
  > 先遞迴收集被刪圖形及其群組子孫到一個 HashSet，移除選取的圖形後，再用 `removeIf` 逐一詢問每個圖形 `isAttachedToAny(集合)`。只有 ConnectionLine 覆寫這個方法，起點或終點的主人在集合裡就回傳 true，被一起刪除。用多型查詢，Canvas 不需要 instanceof。

- **為什麼要遞迴收集群組子孫？**
  > 連線的 Port 屬於群組裡面的 BasicObject，而不是群組本身。只放群組的話，連到群組內物件的線會判斷不出依附關係而被留下。

- **連線怎麼判斷被點中？**
  > `Line2D.ptSegDist` 算點到線段的最短距離，5 像素內就算點中。連線在最底層，所以和物件重疊時會優先選到物件。

- **存檔為什麼要整個清單一次 writeObject？**
  > Java 序列化在同一次寫入會記住寫過的物件，重複的物件只寫參照編號，讀回時連線參照的 Port 與物件持有的 Port 仍是同一個物件，連線才會繼續跟著物件移動。

- **反序列化有什麼風險？怎麼防？**
  > `readObject` 會依檔案內容建立任意可序列化類別的物件，惡意檔案可以利用 Gadget Chain 在讀檔時執行程式碼。用 JDK 9 的 `ObjectInputFilter` 設白名單，只允許 shape 套件與必要的 JDK 類別，其他一律拒絕，並限制深度、數量與大小。

- **serialVersionUID 是做什麼的？**
  > 序列化的版本號。讀檔時比對檔案與類別的版本號，不一致就拒絕。不宣告的話 JVM 會自動計算，類別稍微改動就會變，舊檔就讀不回來。

- **匯出 PNG 為什麼不用改每個圖形的 draw？**
  > `BufferedImage.createGraphics()` 給的也是 Graphics API，draw 只認得畫筆，不在乎畫在螢幕還是影像上。匯出前暫時清除選取與懸停狀態，畫完再還原，所以圖片裡沒有控制點。

- **為什麼標籤原本沒有置中？**
  > `drawString` 的 x 是文字最左端、y 是基線，直接傳中心點會讓文字偏右又偏上。改用 FontMetrics 量出文字寬度與高度，扣掉後除以二，y 再加上 ascent 換算成基線。

- **連線箭頭為什麼會被遮住？怎麼修？**
  > 連線整條畫在最底層，但箭頭尖端在物件邊緣，斜向靠近時有一半在物件內部，被後畫的物件蓋掉。修法是拆成兩輪：線身用 draw 留在底層，箭頭用 drawOverlay 在所有物件畫完後才畫。drawOverlay 是 Shape 上預設空實作的多型掛勾，只有 ConnectionLine 覆寫。

- **為什麼連線不能被收進群組？**
  > 連線的 x/y/width/height 沒有意義，收進群組會讓 updateBounds 算出錯的外框；而且連線綁在 Port 上，物件移動時線本來就會跟著走，不需要群組管理。
